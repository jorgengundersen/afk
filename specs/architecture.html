Architecture

afk is a small Go command-line program built with the standard library first. The architecture should stay boring: parse flags, validate a config, run a loop, execute child processes, return an exit code.

1. Scope Boundary

The binary is only the generic loop runner defined by the PRD. Do not add agents, harnesses, models, prompts, beads clients, structured child-output parsing, renderers, config files, persistent state, or session logs.

2. Initial Repository Shape

go.mod
cmd/afk/main.go
internal/afk/config.go      // flags, config, validation
internal/afk/duration.go    // duration parsing helpers
internal/afk/items.go       // item parsing and item source refresh
internal/afk/policy.go      // failure and final-exit decisions
internal/afk/loop.go        // loop orchestration
internal/afk/exec.go        // child process execution boundary
internal/afk/signal.go      // interrupt handling boundary

Use one internal package at first. Add packages or interfaces only when a real boundary earns the cost.

3. Main Flow

  1. main calls an internal entrypoint and exits with its code.
  2. Parse arguments before -- as afk flags.
  3. Require the command after --; execute it exactly as provided.
  4. Validate the full config before running anything.
  5. Install interrupt handling.
  6. Run the selected loop driver.
  7. Map child exits, source errors, timeouts, and interrupts to final exit codes.

4. Core Types

TypePurpose
ConfigValidated CLI configuration and command argv.
LoopDriverFixed count, daemon, static items, or dynamic items.
ItemBatchCurrent parsed item batch and per-batch indexes.
InvocationOne child command run: argv, env additions, timeout.
RunResultChild exit code plus timeout/interruption metadata.

Keep these as plain structs and small functions. Avoid object hierarchies, frameworks, global mutable state, and hidden defaults.

5. Pure Logic

These functions should be easy to unit test without processes or sleeps:

  • flag/config validation
  • duration parsing
  • JSON-array and newline item parsing
  • environment variable construction
  • failure-policy and final-exit decisions

6. External Boundaries

  • Use os/exec for processes.
  • The command after -- is executed directly, not through a shell.
  • --items-cmd is a shell command and is run as /bin/sh -c on Unix-like systems.
  • Child stdout, stderr, and stdin are inherited/pass-through by default.
  • --items-cmd stdout is captured for item parsing; its stderr is written to afk stderr.
  • Non-zero --items-cmd exit is an afk source error.
  • Use timers from time and signals from os/signal.

7. Process Management

v1 targets Unix-like systems. Start each child command in its own process group. On timeout or interrupt, terminate the process group, wait a short grace period, then kill it if needed. Interrupt exit code is 130.

--timeout applies to each command invocation after --. It does not add a separate timeout for --items-cmd.

8. Duration Contract

Parse durations with Go's time.ParseDuration. Examples: 500ms, 10s, 5m, 1h. --sleep must be non-negative. --timeout, when set, must be positive.

9. Output Contract

afk never writes control output to stdout. Stdout belongs to the child command. Human-readable status and errors, if printed, go to stderr and should be minimal.

10. Exit Codes

  • 0: requested work completed successfully under the selected policy.
  • child exit code: used when --fail stop stops on a child failure, or fixed --until-success attempts are exhausted.
  • 1: internal error, source command failure, or timeout-management failure.
  • 2: invalid CLI usage/configuration.
  • 130: user interrupt.
