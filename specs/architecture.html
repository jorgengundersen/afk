Architecture

afk is a small Go command-line program built with the standard library first. The architecture should stay boring: parse flags, validate a config, run a loop, execute child processes, return an exit code.

1. Scope Boundary

The binary is only the generic loop runner defined by the PRD. Do not add integrations for specific tools, services, workflows, or domains. Do not add child-output interpretation, renderers, config files, persistent state, or session logs.

2. Platform Scope

afk targets Unix-like systems only: Linux and macOS. Windows support is not a v1 goal and should not shape architecture, tests, command execution, signal handling, or process-group behavior.

3. Build and Toolchain

  • Use Go modules.
  • Use a current stable Go version; set go.mod to Go 1.22 or newer.
  • Build command: go build ./cmd/afk.
  • Test command: go test ./....

4. Initial Repository Shape

go.mod
cmd/afk/main.go
internal/afk/config.go      // flags, config, validation
internal/afk/duration.go    // duration parsing helpers
internal/afk/items.go       // item parsing and item source refresh
internal/afk/policy.go      // failure and final-exit decisions
internal/afk/loop.go        // loop orchestration
internal/afk/exec.go        // child process execution boundary
internal/afk/signal.go      // interrupt handling boundary

Use one internal package at first. Add packages or interfaces only when a real boundary earns the cost.

5. Main Flow

  1. main calls an internal entrypoint and exits with its code.
  2. Recognize -h and --help before separator validation; print usage to stdout and exit 0.
  3. For non-help invocations, require the command separator --.
  4. Parse arguments before -- as afk flags.
  5. Treat arguments after -- as the child command and its arguments; never parse, remove, or rewrite them.
  6. Require the command after --; execute it exactly as provided.
  7. Validate the full config before running anything.
  8. Install interrupt handling.
  9. Run the selected loop driver.
  10. Map child exits, source errors, timeouts, and interrupts to final exit codes.

6. Core Types

TypePurpose
ConfigValidated CLI configuration and command argv.
LoopDriverFixed count, daemon, static items, or dynamic items.
ItemBatchCurrent parsed item batch and per-batch indexes.
InvocationOne child command run: argv, env additions, timeout.
RunResultChild exit code plus timeout/interruption metadata.

Keep these as plain structs and small functions. Avoid object hierarchies, frameworks, global mutable state, and hidden defaults.

7. Pure Logic

These functions should be easy to unit test without processes or sleeps:

  • flag/config validation, including whether flags with defaults were explicitly set when validation depends on explicitness, such as --sleep and --empty-sleeps
  • duration parsing
  • JSON-array and newline item parsing
  • environment variable construction
  • failure-policy and final-exit decisions

8. External Boundaries

  • Use os/exec for processes.
  • The command after -- is executed directly, not through a shell.
  • --items-cmd is a shell command and is run as /bin/sh -c on Unix-like systems.
  • The main command after -- inherits/pass-throughs stdin, stdout, and stderr.
  • The main command's stdout and stderr are not captured, merged, buffered, parsed, prefixed, or transformed by afk.
  • --items-cmd stdout is captured for item parsing and is not echoed to stdout; its stderr is written to afk stderr unchanged.
  • --items-cmd stdin is closed or connected to an empty reader, never inherited from interactive stdin.
  • Non-zero --items-cmd exit is an afk source error.
  • Use timers from time and signals from os/signal.

9. Process and Interrupt Management

Every spawned command runs in its own Unix process group. This includes the main command after -- and --items-cmd. Use Go's standard library plus Unix process attributes such as syscall.SysProcAttr{Setpgid: true}.

9.1 Cleanup Guarantee

On interrupt or timeout, afk signals the whole process group it created, not only the immediate child. It must call Wait for the immediate child before returning. This prevents normal child and grandchild ghost processes.

The guarantee covers processes that remain in the process group created by afk. If a child intentionally daemonizes, calls setsid, changes process group, or double-forks, cleanup is best effort and out of v1 supervisor scope. Interactive terminal programs that require foreground process-group control are not a v1 focus; afk is optimized for unattended commands.

9.2 First Interrupt: Graceful Shutdown

On first SIGINT:

  1. Mark afk as interrupted.
  2. Stop scheduling new iterations.
  3. Wake any active --sleep immediately.
  4. If a main command or --items-cmd is running, send SIGINT to its process group.
  5. Wait up to 5s.
  6. If still running, send SIGTERM to the process group.
  7. Wait up to 2s.
  8. If still running, send SIGKILL to the process group.
  9. Wait for the immediate child and exit 130.

9.3 Second Interrupt: Hard Shutdown

If another SIGINT arrives while graceful shutdown is in progress, immediately send SIGKILL to the current process group, wait up to 500ms for the immediate child, and exit 130. Do not wait through the graceful timers again.

9.4 Timeout Shutdown

--timeout applies to every command process group started by afk: the main command after -- and --items-cmd. On timeout, terminate the process group with SIGTERM, wait up to 2s, then send SIGKILL if still running.

A main command timeout is treated as a child failure and handled by the selected failure policy. An --items-cmd timeout is an afk source error and exits 1.

10. Sleep Contract

Sleeps must be interruptible. A Ctrl+C during --sleep exits promptly with 130; it must not wait for the full sleep duration.

11. Duration Contract

Parse durations with Go's time.ParseDuration. Examples: 500ms, 10s, 5m, 1h. --sleep must be non-negative. --timeout, when set, must be positive.

12. Output Contract

afk never writes control output to stdout, except explicit help output. Stdout belongs to the child command. Routine per-iteration status is disabled by default. Errors, usage failures, timeout messages, interrupt messages, and other required diagnostics go to stderr and should be minimal.

13. Exit Codes

  • 0: requested work completed successfully under the selected policy.
  • child exit code: used when --fail stop stops on a child failure, or fixed --until-success attempts are exhausted.
  • 126/127: immediate main-child start failure exits for cannot-execute/not-found. These do not follow --fail or --until-success.
  • 124: synthetic main-child exit code for timeout when surfaced by the selected failure policy.
  • 1: internal error, source command failure, or timeout-management failure.
  • 2: invalid CLI usage/configuration.
  • 130: user interrupt.
