Coding and Testing Standards

Optimize for simple, solid, boring Go. The code should be easy for a new human or agent to read in one pass.

1. Coding Standards

  • Use the Go standard library by default.
  • Do not add dependencies without a clear issue and spec update.
  • Prefer direct code over clever abstractions.
  • Keep functions small and name them after the one thing they do.
  • Keep data as plain structs and values.
  • Pass dependencies explicitly. Avoid package-level mutable state.
  • Return errors with context; handle them at entrypoints.
  • Use errors.Is/errors.As only when callers need typed behavior.
  • Run gofmt. Do not hand-format Go code.
  • Delete stale code instead of adapting removed product scope.

2. Implementation Patterns

Keep orchestration thin and push decisions into small, named functions. These examples show shape, not full implementations.

2.1 Entrypoint

main should wire process IO and exit. It should not contain loop logic.

func main() {
    os.Exit(afk.Main(os.Args[1:], os.Stdin, os.Stdout, os.Stderr))
}

2.2 Config Is Data

Prefer plain structs and validation functions over objects with hidden behavior.

type Config struct {
    Loops   int
    Daemon  bool
    Command []string
}

func ValidateConfig(cfg Config) error { /* small checks only */ }

2.3 Pure Functions First

Parsing and policy should not touch processes, files, sleeps, or globals.

func ParseItems(s string) ([]string, error)
func EnvForIteration(index int, item *ItemContext) []string
func ExitAfterFailure(policy FailurePolicy, code int) Decision

2.4 Narrow Boundaries

Only boundary code imports process/signal packages. Domain logic receives simple values.

// exec.go owns os/exec, syscall, process groups.
func RunInvocation(ctx context.Context, inv Invocation) RunResult

// loop.go decides what to run next. It does not build exec.Cmd.

2.5 Dependency Direction

  • config.go parses and validates; it does not run loops.
  • items.go parses item text; it does not execute child work.
  • policy.go maps result codes to decisions; it does not sleep.
  • exec.go runs one process; it does not know item semantics.
  • loop.go orchestrates; it should stay readable and small.

2.6 Avoid God Objects

Do not create one struct that owns config, parsing, policy, process state, logging, and tests.

// Avoid:
type App struct { /* config + parser + loop + exec + signals + output */ }
func (a *App) RunEverything() error

// Prefer:
cfg, err := ParseArgs(args)
code := RunLoop(ctx, cfg, runner, stderr)

2.7 Interfaces Must Earn Their Cost

Start with functions. Add tiny interfaces only at hard external boundaries.

// Good if tests need a fake runner:
type Runner interface {
    Run(context.Context, Invocation) RunResult
}

2.8 Concurrency Rule

Use goroutines only to wait for child processes, handle signals, or implement timeouts. Do not introduce worker pools, event buses, pipelines, or global channels for v1.

3. Anti-Patterns to Avoid

  • Large Run functions that parse flags, parse items, spawn processes, and decide policy together.
  • Package globals for current config, current child PID, writers, or interrupt state.
  • Parsing main child stdout or stderr for meaning.
  • Shell-wrapping the main child command after --.
  • Sleeping with time.Sleep where interruptible sleep is required.
  • Adding abstractions before there are two real callers.
  • Tests that assert private helper call order instead of observable behavior.

4. Forbidden Scope

  • No agent, harness, model, or prompt concepts.
  • No beads client integration or workflow orchestration.
  • No structured parsing/rendering of child command output.
  • No config files, file logging, session state, or plugin systems in v1.
  • No Windows-specific code, abstractions, compatibility layers, or tests in v1.
  • No concurrency unless required for process timeout, signal, or pipe handling.

5. Error Standards

  • Invalid flags/configuration are usage errors and exit 2.
  • Source command failures and internal failures exit 1.
  • Child command failures are loop inputs, not automatically afk errors.
  • Error messages go to stderr and should say what failed and why.
  • Do not print stack traces or debug dumps in normal operation.

6. Output Standards

  • Never write afk status/control text to stdout, except explicit help output.
  • Main child stdout and stderr must pass through unchanged on their original streams.
  • Do not merge stdout and stderr, prefix child lines, strip bytes, or reinterpret encodings.
  • --items-cmd stdout is captured as item-source data, not passed through; its stderr is passed through unchanged.
  • Routine per-iteration status is disabled by default in v1.
  • Required errors, usage errors, timeout messages, and interrupt messages are minimal, human-readable, and stderr-only.

7. Testing Standards

  • Use Go's standard testing package.
  • Project-wide test command: go test ./....
  • Build command for black-box CLI tests and manual checks: go build ./cmd/afk.
  • Prefer black-box CLI tests for product behavior.
  • Unit-test pure functions: validation, durations, item parsing, env construction, exit policy.
  • Do not test implementation details that are not contract.
  • Each bug fix should add a failing test when practical.
  • Tests must be deterministic: no network, no real beads commands, no long sleeps.
  • Use temporary directories/files from t.TempDir.
  • Use short timeouts and contexts around subprocess tests to prevent hangs.
  • Signal and timeout tests may use tiny helper shell commands and only need to work on Linux/macOS.
  • Interrupt tests should prove graceful shutdown, hard second interrupt, interruptible sleep, and process-group cleanup.
  • Assert stdout exactly when testing child output passthrough and help output.
  • Assert stderr only for required errors or broad required behavior.

8. Test Patterns

8.1 Table-Driven Pure Tests

for _, tc := range tests {
    t.Run(tc.name, func(t *testing.T) {
        got, err := ParseItems(tc.input)
        if !reflect.DeepEqual(got, tc.want) { t.Fatalf("...") }
        if (err != nil) != tc.wantErr { t.Fatalf("...") }
    })
}

8.2 Black-Box CLI Tests

Build the binary once per package test and assert exit code, stdout, and required stderr behavior.

cmd := exec.Command(bin, "-n", "3", "--", "printf", "hi\\n")
out, err := cmd.Output()
code := exitCode(err)
if code != 0 || string(out) != "hi\nhi\nhi\n" { t.Fatalf("...") }

8.3 Process Tests

Use short deadlines, temp files for synchronization, and cleanup checks. Never rely on long real sleeps.

9. Test Matrix

  • -n runs exactly N times and sets AFK_INDEX.
  • Static newline items run once per non-blank line.
  • Static JSON array items run once per element.
  • Dynamic --items-cmd refreshes batches and handles empty batches.
  • --sleep only applies to empty dynamic item batches.
  • --fail continue, --fail stop, and --until-success produce documented exit behavior.
  • --timeout terminates a hung main child process group and applies failure policy.
  • --timeout terminates a hung --items-cmd process group and exits 1.
  • The command separator -- is required.
  • Unknown flags, missing child command, and invalid flag combinations exit 2.
  • -h and --help print usage to stdout and exit 0.
  • Source command failure exits 1.
  • Main child not-found and cannot-execute start failures map to synthetic child codes 127 and 126, then follow failure policy.
  • Ctrl+C during a child sends graceful interrupt and exits 130.
  • A second Ctrl+C hard-kills the active child process group and exits 130.
  • Ctrl+C during empty-source sleep wakes immediately and exits 130.
  • Grandchildren that remain in the child process group are cleaned up.
  • A running --items-cmd is also killed as a process group on interrupt.
  • --items-cmd does not inherit stale AFK_* loop-context variables.
  • Non-item main child invocations remove stale item context variables.

10. Done Criteria

  • gofmt applied.
  • go build ./cmd/afk succeeds.
  • go test ./... passes.
  • Behavior matches the PRD and architecture specs.
  • No removed-scope concepts were introduced.
