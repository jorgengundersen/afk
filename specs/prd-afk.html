PRD: Simplified afk Loop Utility

Draft A radically simplified, general-purpose loop runner.

1. Product Summary

afk should be a small, general-purpose utility for repeatedly running a main child command. It should not know what that command does. It should not parse the command's output. Behavior, logging, workflow logic, network access, and domain-specific handling belong in the command or script that afk runs.

Core contract:

afk repeatedly executes one main child command. It may optionally choose main child invocations from an item list. It passes loop context to the main child through environment variables. For the main child, afk decides whether to continue based only on the child exit status and the selected failure policy. Dynamic item-source command failures are afk source errors, not loop-input failures.

The CLI shape is:

afk [loop options] -- command [args...]

Everything after -- is the main child command and its arguments. afk does not parse, remove, rewrite, or shell-wrap those arguments.

2. Goals

  • Run any command repeatedly.
  • Support fixed loop counts.
  • Support daemon mode: loop until interrupted.
  • Optionally drive loops from a static item list.
  • Optionally drive loops from a dynamic item-producing command.
  • Support newline-delimited and JSON-array item formats.
  • Sleep when a dynamic item source has no items.
  • Apply simple exit-status policies to main child command results.
  • Support a per-invocation timeout for each spawned main child command and dynamic item-source command so unattended loops cannot hang forever on one process group.

3. Non-goals

  • No integrations for specific tools, services, workflows, or domains.
  • No main child command output interpretation, summarization, routing, parsing, or rendering.
  • No main child command input generation beyond environment variables defined by this spec. afk does not synthesize stdin or command arguments for the main child.
  • No placeholder substitution such as {item}.
  • No file logging in v1.
  • No config files in v1.
  • No concurrent main child command execution, worker pools, or parallel loop processing in v1. afk runs at most one spawned command process group at a time. Internal goroutines are allowed only for process waiting, signal handling, timeout handling, or pipe handling.

4. CLI

5. Run Modes

5.1 Fixed count

Run the main child command exactly N times unless interrupted or stopped early by the selected failure policy. A timed-out main child invocation counts as one attempted iteration and is handled by that policy as synthetic main child exit code 124.

afk -n 5 -- make test

5.2 Daemon

Run the main child command until interrupted. Without --items-cmd, daemon mode runs main child invocations back-to-back with no built-in delay. If pacing is needed, put the sleep in the main child command.

afk -d -- ./worker

5.3 Static item list

--items provides an already-materialized item list. It is parsed once before any main child invocation. The main child command runs once per parsed item, in source order. 

afk --items "$(cat my_list.txt)" -- ./worker
afk --items '["a","b","c"]' -- ./worker

5.4 Dynamic item command

--items-cmd provides a dynamic item-source shell command that produces one item batch per invocation. afk runs this command to refresh available work. This is what makes daemon polling possible. 

afk -d --items-cmd "./list-work" --sleep 5m -- ./worker

The item-source command stdout may contain either newline-delimited text or a JSON array. For example, ./list-work and some-command --json are both valid item-source shapes if their stdout matches one of those formats.

V1 behavior:

  • Invoke --items-cmd once to produce the next item batch.
  • If that invocation exits non-zero, discard any captured stdout from that invocation, treat it as a source error, and exit 1.
  • Each invocation captures at most 8 MiB of stdout for item parsing. If stdout exceeds that size, discard the captured stdout from that invocation, treat it as a source error, and exit 1.
  • If that invocation produces one or more parsed items, process that batch one item at a time, in batch order, by running the main child command once per item.
  • In non-daemon mode, after fully processing the first non-empty batch, exit 0 unless stopped earlier by the selected main child failure policy or another documented error condition.
  • In daemon mode, after the current batch is exhausted, invoke --items-cmd again to fetch the next batch.
  • If an invocation produces an empty item batch in daemon mode, sleep for --sleep and then invoke --items-cmd again, repeating until interrupted or a non-empty batch is found.
  • If an invocation produces an empty item batch in non-daemon mode, sleep for --sleep and retry while --empty-sleeps quota remains; if no non-empty batch is found after those retries, exit 0.
  • With --empty-sleeps 0, the first successful empty batch in non-daemon mode exits 0 immediately without sleeping.
  • Empty-batch sleep/retry cycles do not increment AFK_INDEX; AFK_INDEX increments only for main child invocations.

6. Item Parsing

6.1 JSON array

If item-source stdout is valid JSON and the top-level value is an array, each array element is one item.

  • String elements become their string value.
  • Number, boolean, object, array, and null elements become compact JSON in AFK_ITEM. Whitespace is removed. Object key order is not part of the contract; callers and tests must treat object output as JSON, not byte-identical text.
  • An empty array means no items.
  • If item-source stdout is valid JSON but the top-level value is not an array, parse the original stdout bytes as newline-delimited text instead.

6.2 Newline-delimited text

If item-source stdout is not a JSON array, parse the original stdout bytes as newline-delimited text.

  • Delimiter is \n; standalone \r is not a delimiter.
  • Trailing final newline is ignored.
  • For CRLF input, one trailing \r immediately before a line-ending \n is removed as part of line-ending removal.
  • Other \r bytes in non-blank lines are preserved as item content.
  • A line is blank if trimming Unicode whitespace leaves an empty string.
  • Blank lines are ignored.
  • Non-blank line content is preserved exactly except for line-ending removal.

6.3 Empty item sources

  • --items "" means no items and exits 0.
  • Whitespace-only newline text means no non-blank items and exits 0.
  • --items "[]" means no items and exits 0.
  • An empty batch from --items-cmd follows the dynamic empty-batch sleep/retry rules in sections 5 and 8.
  • Static item sources never sleep.

6.4 Source exclusivity

Only one item source may be set:

  • --items
  • --items-cmd

7. Environment Variables

afk never rewrites the main child command. It passes loop context to main child invocations through environment variables.

VariableSet whenMeaning
AFK_INDEX Always 1-based global main child invocation number.
AFK_ITEM Item-driven loops Current item value. JSON objects/arrays are compact JSON.
AFK_ITEM_INDEX Item-driven loops 0-based index of the item within the current batch.
AFK_ITEM_COUNT Item-driven loops Total number of items in the current batch.

For each main child invocation, afk constructs the child environment from the parent environment plus loop context. It always overrides AFK_INDEX. In item-driven loops, it also overrides AFK_ITEM, AFK_ITEM_INDEX, and AFK_ITEM_COUNT. In non-item loops, inherited AFK_ITEM, AFK_ITEM_INDEX, and AFK_ITEM_COUNT are removed so unrelated item context cannot leak into the main child. Each --items-cmd invocation receives the parent environment with AFK_INDEX, AFK_ITEM, AFK_ITEM_INDEX, and AFK_ITEM_COUNT removed; it gets no loop context because it runs before the next main child invocation exists. 

afk --items '["apple","banana"]' -- sh -c 'echo "$AFK_INDEX $AFK_ITEM_INDEX/$AFK_ITEM_COUNT $AFK_ITEM"'

Expected output:

1 0/2 apple
2 1/2 banana

8. Sleep Semantics

In v1, --sleep only means: how long to wait when --items-cmd produces an empty item batch. It does not sleep between successful main child invocations.

8.1 Daemon mode

afk -d --items-cmd "./list-work" --sleep 5m -- ./worker

If an invocation produces an empty item batch, sleep for five minutes, then invoke --items-cmd again.

8.2 Non-daemon mode

afk --items-cmd "./list-work" --empty-sleeps 3 --sleep 30s -- ./worker

If an invocation produces an empty item batch, sleep and retry up to three times. Sleeps do not count as main child invocations.

8.3 Sleeping between all loops

No dedicated flag in v1. Users can put sleep in the main child command if needed: 

afk -n 10 -- sh -c './worker; sleep 5'

9. Failure Policy

For the main child command, afk only observes the exit status. Main child stdout and stderr are not interpreted.

PolicyBehaviorExample
--fail continue Non-zero main child exit statuses are treated as loop input, but the loop continues. afk -n 20 --fail continue -- ./worker
--fail stop First non-zero main child exit status stops the loop. afk exits with that status code. afk -n 5 --fail stop -- go test ./...
--until-success Failures continue; the first zero main child exit status stops the loop with exit code 0. afk -d --until-success -- curl -f http://localhost:3000/health

Effective failure-policy selection in v1:

  • If --until-success is set, the effective failure policy is --until-success.
  • Otherwise, if --fail is explicitly set, the effective failure policy is the explicit --fail value.
  • Otherwise, the effective failure policy defaults to --fail continue.

V1 final exit behavior:

  • Under --fail continue with --loops, exit 0 after all requested main child invocations complete, regardless of non-zero main child exit codes, unless a documented afk error or user interrupt occurs.
  • Under --fail continue with item-driven loops, exit 0 after the requested item-driven work completes, regardless of non-zero main child exit codes, unless a documented afk error or user interrupt occurs.
  • Under --fail continue with --daemon, continue until interrupted or until a documented afk error occurs.
  • Under --fail stop, stop at the first non-zero main child exit code and exit with that code.
  • Under --until-success with --loops, exit 0 on the first successful main child exit; if all fixed attempts are exhausted, exit with the last non-zero main child exit code, or 1 if none is available.
  • Under --until-success with --daemon, continue until the first successful main child exit, then exit 0; if interrupted first, exit 130.
  • Main child start failures (126/127) and source errors (1) bypass failure policy and exit immediately with their documented codes.
  • Interrupted by signal: exit 130.
  • Invalid usage/configuration: exit 2.
  • Internal error, source command failure, or timeout-management failure: exit 1.

10. Timeout

--timeout limits each command process group started by afk: both the main child command and --items-cmd. It prevents an unattended loop from getting stuck forever on one hung spawned process group. 

afk -n 10 --timeout 30m -- ./worker

If the main child command times out, afk sends SIGTERM to that process group, waits up to 2s, then sends SIGKILL if needed, and treats the iteration as synthetic main child exit code 124; that result is then handled by the selected failure policy. If --items-cmd times out, afk applies the same timeout cleanup to that process group and then exits 1 as a source error.

11. Output

Main child stdout and stderr pass through directly. afk does not parse, render, or transform main child output. --items-cmd stdout is item-source data and is captured for parsing with a maximum captured size of 8 MiB per invocation; if a --items-cmd invocation exits non-zero, times out, or exceeds that capture limit, its captured stdout is discarded and not parsed as items. Its stderr passes through unchanged.

By default, afk prints no routine status lines. Stdout belongs to the main child command, except for explicit CLI help output such as --help. afk diagnostics, usage errors, timeout messages, interrupt messages, and other control output go to stderr and should be minimal.

No file logging in v1. If users need logs, they can redirect output or make the main child command log for itself.

12. Signals and Process Management

Every spawned command runs in its own Unix process group. On interrupt or timeout, afk signals the whole process group it created, not only the immediate child. The interrupt sequence in this section applies to user interrupts; timeout cleanup follows the timeout sequence defined in section 10.

  • On first SIGINT, mark afk as interrupted, stop scheduling new iterations, and wake any active --sleep immediately.
  • If a main child command or --items-cmd invocation is running, send SIGINT to its process group.
  • Wait up to 5s, then send SIGTERM to the process group if still running.
  • Wait up to 2s, then send SIGKILL to the process group if still running.
  • If another SIGINT arrives during graceful shutdown, immediately send SIGKILL to the current process group.
  • After normal interrupt shutdown, and after timeout shutdown as defined in section 10, wait for the immediate child before returning.
  • After second-interrupt hard shutdown, wait up to 500ms for the immediate child, then exit 130.
  • Exit with code 130 on user interrupt.

13. Validation Rules

  • The command separator -- is required, except for -h and --help as defined in section 4.
  • A main child command after the first -- is required.
  • Unknown afk flags exit 2.
  • At least one loop driver is required: --loops, --daemon, --items, or --items-cmd.
  • --items "", whitespace-only newline text in --items, and --items "[]" are valid item-driven configurations; they produce zero main child invocations and exit 0.
  • --loops must be a positive integer.
  • --loops and --daemon are mutually exclusive.
  • --loops and item sources are mutually exclusive, because both determine main child invocation count.
  • --items and --items-cmd are mutually exclusive.
  • --daemon may be combined with --items-cmd.
  • --daemon and --items are mutually exclusive, to avoid replaying a static list forever.
  • The default values of --sleep and --empty-sleeps do not by themselves make those flags explicit. Their explicit-use restrictions apply only when the user sets them on the CLI.
  • Explicit --sleep is valid only with --items-cmd and must be non-negative.
  • Explicit --empty-sleeps is valid only with --items-cmd and must be non-negative.
  • --fail must be continue or stop.
  • If neither --until-success nor an explicit --fail flag is provided, the effective failure policy is --fail continue.
  • --until-success is mutually exclusive with any explicit --fail flag, including --fail continue and --fail stop.
  • --until-success requires --loops or --daemon and is invalid with item sources in v1.
  • --timeout, when set, must be positive.
  • All invalid combinations exit 2.

14. Examples

Run a main child command five times

afk -n 5 -- echo hi

Run once per newline item

afk --items $'a\nb\nc' -- sh -c 'echo "$AFK_ITEM"'

Run once per JSON item

afk --items '[{"id":"a"},{"id":"b"}]' -- sh -c 'echo "$AFK_ITEM" | jq -r .id'

Empty static item list exits 0 without running the main child

afk --items '[]' -- ./worker

Poll a dynamic work source forever

afk -d --items-cmd "./list-work" --sleep 5m -- ./worker

Retry until a service is healthy

afk -d --until-success --timeout 15s -- sh -c 'curl -f http://localhost:3000/health || { sleep 10; exit 1; }'

Default failure policy continues fixed-count work

afk -n 3 -- sh -c 'echo "attempt $AFK_INDEX"; exit 1'

Strict failure behavior

afk -n 5 --fail stop -- go test ./...

Failing dynamic item source exits 1

afk --items-cmd "exit 3" -- ./worker

Help does not require a separator

afk --help

15. Acceptance Criteria

  • afk -n 3 -- echo hi prints hi three times and exits 0.
  • afk -n 3 -- sh -c 'exit 7' uses the default effective failure policy --fail continue, attempts three main child invocations, and exits 0.
  • afk --items $'a\nb' -- sh -c 'echo "$AFK_ITEM"' prints a then b.
  • afk --items '["a","b"]' -- sh -c 'echo "$AFK_ITEM"' prints a then b.
  • afk --items '[]' -- sh -c 'echo should-not-run' performs zero main child invocations, prints nothing, and exits 0.
  • afk --items-cmd "printf 'a\nb\n'" -- sh -c 'echo "$AFK_ITEM"' processes one non-empty dynamic batch, runs twice, and exits 0.
  • When --items-cmd produces an empty item batch in daemon mode, afk sleeps and retries.
  • When --items-cmd produces an empty item batch in non-daemon mode, afk respects --empty-sleeps and exits 0 if no non-empty batch is found.
  • With --empty-sleeps 0, the first successful empty --items-cmd batch in non-daemon mode exits 0 without sleeping.
  • AFK_INDEX is set for every main child invocation.
  • AFK_ITEM, AFK_ITEM_INDEX, and AFK_ITEM_COUNT are set for item-driven invocations.
  • --fail stop stops on the first non-zero main child exit status and exits with that status code.
  • --until-success stops on the first zero main child exit status.
  • afk --help prints usage to stdout, exits 0, and does not require --.
  • Unknown flags, missing main child command, and invalid flag combinations exit 2.
  • A non-zero --items-cmd exit discards that invocation's captured stdout, is treated as a source error, and exits 1.
  • If --items-cmd stdout exceeds 8 MiB in one invocation, afk discards that invocation's captured stdout, treats it as a source error, and exits 1.
  • --timeout terminates a hung main child process group and applies failure policy.
  • --timeout terminates a hung --items-cmd process group and exits 1.
  • Main child stdout/stderr are passed through unchanged on their original streams.
  • Main child command not found exits 127, and main child command cannot execute exits 126; both bypass failure policy.
  • Ctrl+C terminates the current spawned process group, if any, and exits 130.

16. Explicitly Deferred

  • --items-file — users can use --items "$(cat file)" or --items-cmd "cat file".
  • Placeholder substitution like {item}.
  • A dedicated interval flag for sleeping between every successful loop.
  • Quiet/verbose modes.
  • Dry-run mode.
  • File logging.
  • Config files.
  • Parallel execution.
  • --version.
